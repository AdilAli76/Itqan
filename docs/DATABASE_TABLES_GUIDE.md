## 1. القواعد العامة الثابتة في كل جدول

قبل شرح أي جدول بمفرده، هذه القواعد تنطبق على **كل** جدول تشغيلي في النظام، وفهمها أولاً يجعل شرح كل جدول لاحقاً أقصر وأوضح:

### 1.1 المفتاح الأساسي دائماً `UNIQUEIDENTIFIER` (GUID) وليس رقماً متسلسلاً (`INT IDENTITY`)
**لماذا:** لو استخدمنا `INT IDENTITY`، فلو دُمجت بيانات فرعين أو زبونين مستقبلاً (مثلاً عند الترقية من نسخة منفصلة إلى نسخة سحابية موحّدة)، ستتصادم الأرقام (فرع 1 عند الزبون أ يصطدم مع فرع 1 عند الزبون ب). الـ GUID فريد عالمياً بلا تصادم أبداً، وهذا **شرط أساسي لأي نظام يُباع لأكثر من زبون**.
**الكلفة المقبولة:** حجم أكبر قليلاً في الفهرس مقارنة بـ INT، وهو فرق مقبول تماماً في نظام ERP تجاري بحجم البيانات المتوقع (آلاف إلى ملايين الصفوف، وليس مليارات).

### 1.2 `organization_id` — موجود في كل جدول تقريباً
كل جدول تشغيلي (منتجات، فواتير، عملاء...) يحمل `organization_id` يشير إلى الزبون المالك للبيانات. هذا هو أساس العزل بين الزبائن (Multi-Tenant)، ويُطبَّق تلقائياً عبر Security Policy (راجع قسم الحماية في `DATABASE_SCHEMA_SQLSERVER.sql`) — **لا يحتاج أي مطوّر لاحقاً كتابة `WHERE organization_id = ...` يدوياً في أي استعلام جديد**، لأن قاعدة البيانات نفسها ترفض إرجاع صفوف منظمة أخرى.

### 1.3 `branch_id` — موجود في الجداول "التشغيلية اليومية" فقط
ليس كل جدول يحتاج `branch_id`. القاعدة البسيطة:
- **يحتاجه:** أي جدول يمثّل نشاطاً يومياً يحدث *داخل* فرع معيّن (فاتورة، مستوى مخزون، وردية كاشير، مصروف).
- **لا يحتاجه:** أي جدول يمثّل "تعريفاً" على مستوى الشركة كلها ويُشارك بين كل الفروع (المنتجات نفسها، فئات المنتجات، العملاء أنفسهم كسجل مركزي).
- **قيمة `NULL` في `branch_id` عند المستخدمين تحديداً تعني "مدير عام يرى كل الفروع"** — هذا استثناء مقصود ومهم جداً، مذكور صراحة في تعليقات الكود.

### 1.4 لا حذف فعلي (`is_deleted` بدل `DELETE`)
لاحظ أن الجداول المالية والمخزونية (`products`, `customers`, `suppliers`) تحمل عمود `is_deleted BIT` بدل استخدام أمر `DELETE` الفعلي. **السبب:** فاتورة تشير إلى منتج محذوف يجب أن تبقى قابلة للعرض في التقارير التاريخية. حذف الصف فعلياً يكسر كل فاتورة قديمة تشير إليه (أو يتطلب `ON DELETE CASCADE` يحذف فواتير حقيقية — كارثة محاسبية). كل استعلام قراءة على هذه الجداول **يجب** أن يضيف `WHERE is_deleted = 0`.

### 1.5 أعمدة التوقيت: `created_at` دائماً، `updated_at` عند الحاجة
`created_at DATETIME2 DEFAULT SYSUTCDATETIME()` موجود في كل جدول تقريباً — بتوقيت UTC دائماً (وليس التوقيت المحلي لليبيا) لتفادي مشاكل انتقال بيانات بين مناطق زمنية مستقبلاً؛ التحويل إلى توقيت ليبيا (UTC+2) يحدث في طبقة العرض (Flutter) فقط، وليس في قاعدة البيانات.

### 1.6 لماذا `DECIMAL(14,2)` للمبالغ المالية وليس `FLOAT`
`FLOAT` يُخزّن أرقاماً عشرية بتقريب غير دقيق (Binary Floating Point)، مما يعني أن `0.1 + 0.2` قد لا يساوي `0.3` تماماً — خطأ غير مقبول إطلاقاً في حسابات مالية. `DECIMAL(14,2)` يخزّن الرقم بدقة عشرية حقيقية: 14 خانة إجمالاً، خانتان بعد الفاصلة (يكفي لمبالغ حتى 999,999,999,999.99 د.ل).

### 1.7 لماذا `DECIMAL(14,3)` للكميات (وليس `DECIMAL(14,2)`)
الكميات تحتاج أحياناً دقة ثلاث خانات عشرية (مثلاً 1.250 كجم)، بخلاف المبالغ المالية التي تكفيها خانتان (القروش/الدرهم). لو استخدمنا نفس دقة المبالغ للكميات، ستُفقد دقة الوزن في أي منتج يُباع بالكيلوجرام.

## 2. المجموعة 1: المنظمات والتراخيص

### 2.1 جدول `organizations`
**الغرض:** كل صف = زبون واحد اشترى النظام. هذا هو الجدول الجذر الذي يتفرّع منه كل شيء آخر.

| العمود | النوع | الشرح |
|---|---|---|
| `id` | UNIQUEIDENTIFIER | معرّف المنظمة، يُستخدَم كـ Foreign Key في كل جدول تقريباً في النظام |
| `legal_name` | NVARCHAR(200) | الاسم القانوني الرسمي (يظهر في المستندات الرسمية/الفواتير الضريبية إن وُجدت لاحقاً) |
| `display_name` | NVARCHAR(200) | الاسم المعروض في واجهة النظام — هذا ما يتغيّر عبر شاشة White-Labeling، وليس `legal_name` |
| `logo_url` | NVARCHAR(400) NULL | رابط الشعار المرفوع — `NULL` قبل أول تخصيص، والفرونت إند يتعامل مع هذه الحالة بعرض شعار افتراضي |
| `primary_color` / `secondary_color` | CHAR(7) | كود اللون بصيغة Hex (`#0B2540`) — هذان العمودان تحديداً هما ما يقرأه `AppTheme.build()` في Flutter لحظياً |
| `currency_code` / `currency_symbol` | CHAR(3) / NVARCHAR(10) | افتراضياً LYD / د.ل، لكن الحقل موجود بشكل مستقل حتى يمكن بيع النظام لسوق آخر مستقبلاً دون تعديل الكود، فقط بتغيير هذين الحقلين |
| `locale` | NVARCHAR(5) | لغة الواجهة الافتراضية للمنظمة — `ar` حالياً، الحقل جاهز لإضافة `en` مستقبلاً بدون تعديل البنية |
| `is_active` | BIT | تعطيل كامل للمنظمة (مثلاً عند توقف السداد) بدون حذف بياناتها |

**علاقات:** جدول جذر — لا يشير إلى أي جدول آخر، وكل الجداول الأخرى (تقريباً) تشير إليه.
**فهرسة:** `id` هو المفتاح الأساسي (مفهرس تلقائياً)؛ لا حاجة لفهارس إضافية لأن عدد المنظمات صغير نسبياً (عشرات إلى مئات الزبائن، وليس ملايين).

### 2.2 جدول `licenses`
**الغرض:** هذا الجدول هو الحل التقني لمطلبك التجاري "بيع النظام لأول زبون بشكل متكامل" — يمنع تشغيل النظام بدون ترخيص صالح، ويسمح ببيع خطط مختلفة (Trial/Standard/Professional/Enterprise) لاحقاً دون إعادة بناء الكود.

| العمود | النوع | الشرح |
|---|---|---|
| `id` | UNIQUEIDENTIFIER | معرّف سجل الترخيص |
| `organization_id` | UNIQUEIDENTIFIER (FK) | الترخيص مرتبط بمنظمة واحدة فقط |
| `license_key` | NVARCHAR(100) UNIQUE | المفتاح الذي يُدخله الزبون عند أول تشغيل — فريد عالمياً (`UNIQUE` تمنع تكرار نفس المفتاح لمنظمتين) |
| `plan_tier` | NVARCHAR(20) | يحدد الميزات المتاحة — راجع `enabled_modules` أدناه |
| `max_branches` / `max_users` | INT | حدود الخطة — يتحقق منها الباك إند عند إنشاء فرع/مستخدم جديد (`if (branchCount >= license.MaxBranches) return Forbidden`) |
| `enabled_modules` | NVARCHAR(MAX) (JSON) | مصفوفة نصية بأسماء الموديولات المفعّلة، مثل `["inventory","pos","reports"]` — الباك إند يتحقق من هذا الحقل قبل السماح بالوصول لأي Controller، فتبيع خطة "أساسية" بدون موديول التقارير مثلاً دون فرع كود منفصل |
| `hardware_fingerprint` | NVARCHAR(200) NULL | بصمة الجهاز/السيرفر (مُشتقة من معرّفات الهاردوير) — لخيار On-Premise فقط، تمنع نسخ نفس الترخيص لسيرفر آخر |
| `issued_at` / `expires_at` | DATETIME2 | تاريخ الإصدار والانتهاء — الباك إند يفحص `expires_at` في كل طلب حساس (Middleware مخصص يُبنى لاحقاً بنفس نمط `TenantContextMiddleware`) |
| `status` | NVARCHAR(20) | `active` عادي، `grace_period` بعد الانتهاء مباشرة (قراءة فقط، لا كتابة، لإعطاء الزبون فرصة تجديد بدل توقف مفاجئ يفقد ثقته)، `expired`، `revoked` (إلغاء يدوي من طرفك كبائع) |

**علاقات:** `organization_id → organizations.id` (علاقة واحد لواحد عملياً، رغم أن الجدول يسمح تقنياً بأكثر من ترخيص تاريخي لنفس المنظمة — مفيد لحفظ سجل الترقيات بين الخطط).
**نقطة توسّع مستقبلية:** لإضافة خطة تسعير جديدة، لا تُعدَّل بنية الجدول إطلاقاً — فقط يُضاف اسم جديد للـ `CHECK` الخاص بـ `plan_tier` وصف جديد في `enabled_modules`.

## 3. المجموعة 2: الفروع

### 3.1 جدول `branches`

| العمود | النوع | الشرح |
|---|---|---|
| `id` | UNIQUEIDENTIFIER | معرّف الفرع، يُستخدَم في كل الجداول "التشغيلية اليومية" |
| `organization_id` | UNIQUEIDENTIFIER (FK) | كل فرع ينتمي لمنظمة واحدة |
| `name` | NVARCHAR(150) | اسم الفرع الظاهر في الواجهة، مثل "فرع طرابلس - المركز" |
| `code` | NVARCHAR(20) | رمز مختصر (مثل `TRP-01`) يُستخدَم في ترقيم الفواتير وتقارير مقارنة الفروع بدل الاسم الطويل |
| `address` / `phone` | NVARCHAR | بيانات وصفية تظهر على رأس الفاتورة المطبوعة لهذا الفرع تحديداً |
| `is_active` | BIT | تعطيل فرع (مثلاً إغلاق مؤقت) دون حذف بياناته أو تاريخه |

**قيد فريد مهم:** `UNIQUE (organization_id, code)` — يعني رمز الفرع يجب أن يكون فريداً *داخل نفس المنظمة فقط*، لا عالمياً؛ فزبونان مختلفان يمكن أن يستخدما كلاهما رمز `001` لأول فرع لكل منهما دون تعارض.

## 4. المجموعة 3: المستخدمون والصلاحيات

### 4.1 جدول `app_users`

| العمود | النوع | الشرح |
|---|---|---|
| `id` | UNIQUEIDENTIFIER | معرّف المستخدم — نفس القيمة المستخدَمة في claim `sub` داخل توكن JWT |
| `organization_id` | UNIQUEIDENTIFIER (FK) | كل مستخدم ينتمي لمنظمة واحدة فقط (لا مستخدم "عابر" بين زبونين) |
| `branch_id` | UNIQUEIDENTIFIER NULL (FK) | **`NULL` = مدير عام يرى كل فروع منظمته.** قيمة محدَّدة = مستخدم مقيَّد بفرع واحد فقط. هذا العمود هو ما يقرأه `TenantContextMiddleware` ليضبط `SESSION_CONTEXT('branch_id')` |
| `full_name` | NVARCHAR(150) | الاسم الظاهر في الواجهة وفي سجل التدقيق (من نفّذ العملية) |
| `email` | NVARCHAR(200) | بريد الدخول — فريد *داخل نفس المنظمة* فقط (`UNIQUE(organization_id, email)`), لأن نفس البريد قد يستخدمه موظفان في شركتين مختلفتين اشترتا النظام |
| `password_hash` | NVARCHAR(400) | كلمة المرور مُشفَّرة عبر BCrypt (راجع `AuthController.cs`) — **لا يُخزَّن أي نص صريح لكلمة المرور مطلقاً** |
| `role` | NVARCHAR(30) | الدور الأساسي (يُستخدَم في `[Authorize(Roles = "...")]` في الباك إند) |
| `is_active` | BIT | تعطيل حساب موظف عند مغادرته دون حذف سجله من التقارير التاريخية (من أنشأ أي فاتورة قديمة) |

### 4.2 جدول `permissions`
**الغرض:** صلاحيات دقيقة على مستوى العملية (وليس الدور فقط)، مثل `inventory.edit` أو `pos.refund`. هذا يسمح ببيع خطط مختلفة بصلاحيات مختلفة دون تعديل قاعدة البيانات لاحقاً — راجع `ARCHITECTURE.md §3.4`.

| العمود | النوع | الشرح |
|---|---|---|
| `code` | NVARCHAR(60) PK | المعرّف البرمجي الثابت، مثل `pos.refund` — يُستخدَم في الكود مباشرة، لا يتغيّر أبداً حتى لو تغيّر النص الظاهر |
| `label_ar` | NVARCHAR(150) | النص العربي الظاهر في شاشة إدارة الصلاحيات |
| `module` | NVARCHAR(60) | تجميع الصلاحيات في شاشة الإدارة (مثلاً كل صلاحيات `module = 'inventory'` تظهر في قسم واحد) |

### 4.3 جدول `role_permissions`
**الغرض:** جدول ربط (Many-to-Many) بين الأدوار والصلاحيات، **لكل منظمة على حدة** — بمعنى: منظمة أ يمكنها منح دور "كاشير" صلاحية `pos.refund`، بينما منظمة ب تمنعها عن نفس الدور، دون أن يتعارضا.
المفتاح الأساسي المركّب `(organization_id, role, permission_code)` يمنع تكرار نفس الصلاحية لنفس الدور في نفس المنظمة.

### 4.4 جدول `login_history`
**الغرض:** سجل كل محاولة دخول (ناجحة أو فاشلة) — يُستخدَم في موديول الأمن والتدقيق لرصد محاولات دخول مشبوهة (`success = 0` متكررة من نفس `ip_address`).

| العمود | النوع | الشرح |
|---|---|---|
| `ip_address` | NVARCHAR(50) | عنوان IP وقت المحاولة — يُستخرَج في الباك إند من `HttpContext.Connection.RemoteIpAddress` |
| `device_info` | NVARCHAR(300) | User-Agent المتصفح/الجهاز — مفيد لتمييز "دخول من جهاز غير معتاد" مستقبلاً |
| `success` | BIT | نجحت المحاولة أم فشلت — **يُسجَّل حتى عند الفشل**، وهذا مقصود لأغراض الأمان |

## 5. المجموعة 4: المخزون والموردون

### 5.1 جدول `suppliers`
جدول تعريفي بسيط: اسم المورّد، هاتفه، ورصيده الحالي (`balance` — موجب يعني نحن مدينون له). لا يحمل `branch_id` لأن المورّد عادة يتعامل مع الشركة ككل وليس فرعاً واحداً.

### 5.2 جدول `product_categories`
شجرة فئات (Self-Referencing عبر `parent_id`) — تسمح بفئات فرعية غير محدودة العمق (مثلاً: مواد غذائية ← ألبان ← ألبان مبستَرة) دون تعديل البنية لاحقاً مهما زاد عمق التصنيف.

### 5.3 جدول `products` — الجدول الأكثر أهمية في الموديول
**لماذا لا يحمل `branch_id`:** المنتج "زيت طبخ 1 لتر" هو نفس المنتج بنفس الباركود في كل الفروع؛ ما يختلف بين الفروع هو *الكمية المتوفرة*، وهذا مُخزَّن في جدول منفصل (`stock_levels`) وليس هنا — هذا مبدأ تصميمي أساسي: **تعريف الصنف مركزي، وتوفّره لامركزي (لكل فرع)**.

| العمود | النوع | الشرح |
|---|---|---|
| `sku` | NVARCHAR(60) | رمز الصنف الداخلي — فريد *داخل المنظمة* (`UNIQUE(organization_id, sku)`) |
| `barcode` | NVARCHAR(60) NULL | الباركود المطبوع فعلياً — قد يكون فارغاً لصنف لم يُطبع له باركود بعد؛ **ليس فريداً إجبارياً** لأن بعض المنتجات (خضار موزونة مثلاً) قد تتشارك نفس الباركود الداخلي للوزن |
| `unit_base` | NVARCHAR(30) | وحدة البيع الأساسية (`piece`, `kg`, `box`...) |
| `unit_conversion_factor` | DECIMAL(10,3) | معامل التحويل عند البيع بوحدة أكبر (مثلاً كرتون = 24 قطعة → المعامل = 24) — يُستخدَم في حساب خصم المخزون الصحيح عند بيع كرتون كامل |
| `cost_price` / `sale_price` | DECIMAL(14,2) | سعر التكلفة (لحساب الربح في التقارير) وسعر البيع (الظاهر للعميل) — منفصلان عمداً |
| `track_expiry` | BIT | هل هذا الصنف يحتاج تتبع تاريخ صلاحية؟ (0 لمنتج كالأدوات المكتبية، 1 لمنتج غذائي) — يتحكم في ظهور حقل `expiry_date` في شاشة إضافة المخزون بالفرونت إند |
| `reorder_level` | DECIMAL(14,2) | حد إعادة الطلب — عندما تنخفض الكمية عنه، يُطلَق إشعار تلقائي (راجع `InvoicesController.cs`، القسم الذي يستدعي `LowStockAlert` عبر SignalR) |

### 5.4 جدول `stock_levels` — قلب نظام المخزون متعدد الفروع
**الغرض:** كمية كل منتج في كل فرع، ولكل دفعة (Batch) على حدة — هذا يسمح بتتبع صلاحية دقيق (نفس المنتج قد يكون له دفعتان بتاريخي صلاحية مختلفين في نفس الفرع).

| العمود | النوع | الشرح |
|---|---|---|
| `branch_id` + `product_id` | UNIQUEIDENTIFIER (FK) | معاً يحددان "أي منتج في أي فرع" |
| `quantity` | DECIMAL(14,3) | الكمية المتاحة حالياً |
| `batch_number` | NVARCHAR(60) | رقم الدفعة/التشغيلة — قيمة افتراضية `''` (نص فارغ) للمنتجات التي لا تحتاج تتبع دفعات |
| `expiry_date` | DATE NULL | تاريخ صلاحية هذه الدفعة تحديداً |
| `strategy_date` | DATETIME2 NULL | أساس ترتيب الصرف — انظر أدناه |
| `is_locked` | BIT | الدفعة موقوفة عن الصرف — انظر أدناه |
| `lock_reason` | NVARCHAR(300) NULL | سبب الإيقاف، إلزامي عند القفل |
| `locked_by` / `locked_at` | FK + DATETIME2 | من أوقفها ومتى |

**تاريخ الاستراتيجية — ترتيب الصرف بحقل واحد:** الصيدلية يجب أن تصرف الأقرب انتهاءً، والبقالة تكفيها الأقدم دخولاً. فبدل قاعدتَي ترتيب، تاريخٌ واحد يُملأ بحسب طبيعة الصنف: **تاريخ الانتهاء** للصنف المتتبَّع (⇒ FEFO)، و**تاريخ الإدخال** لغيره (⇒ FIFO). وكل مسار صرف — البيع والتحويل — يرتّب عليه وحده.

العطب الذي يصلحه: الترتيب كان `expiry_date` ثم `batch_number`. والصنف بلا صلاحية كل دفعاته `NULL`، فيسقط الترتيب على رقم الدفعة **أبجدياً** — أي عشوائياً — فتبقى دفعة قديمة على الرفّ لأن رقمها يبدأ بحرف متأخّر.

`NULL` = صنف يتتبّع الصلاحية ووصلت دفعته بلا تاريخ. يُؤخَّر في الصرف عمداً: المعلوم أولى بالتصريف من المجهول. ويُختَم الحقل عند **إنشاء** الصفّ أو تغيّر صلاحيته لا عند كل زيادة كمية (`StockLevel.StampStrategyDate`) — وإلا قفزت الدفعة القديمة إلى آخر الطابور كلما وصلها توريد، وهو نقيض FIFO.

**القفل — إيقاف دفعة في مكانها:** تصل دفعة بشبهة عيب، أو تُرتجع بضاعة تنتظر المعاينة. الحلول الثلاثة الأخرى كلها معطوبة: حذف الصفّ يفقد الكمية ويكسر التدقيق، وتركه يعني بيعها، ونقلها إلى فرع وهمي يشوّه تقارير الفروع.

الموقوف **يخرج من:** البيع (ترتيب FEFO في `InvoicesController`)، وحساب إعادة الطلب، والتحويل بين الفروع. و**يبقى في:** الجرد، وقيمة المخزون، وتقرير الصلاحية — فهو مالٌ مملوك موجود على الرفّ.

وهو **على الدفعة لا الصنف**: ثلاث شحنات من نفس الدواء تُشتبَه واحدة منها، وقفل الصنف كلّه كان يوقف بضاعة سليمة. النقاط في `StockLocksController`.

**قيد فريد:** `UNIQUE(branch_id, product_id, batch_number)` — يمنع وجود صفين لنفس المنتج بنفس الدفعة في نفس الفرع (بدل ذلك، تُحدَّث الكمية في نفس الصف).

### 5.5 جداول `stock_transfers` و `stock_transfer_items`
**الغرض:** تحويل بضاعة بين فرعين — جدول رأس (`stock_transfers`: من فرع، إلى فرع، الحالة) وجدول تفاصيل (`stock_transfer_items`: كل صنف وكميته في هذا التحويل)، بنفس نمط "رأس + تفاصيل" المستخدم في الفواتير وأوامر الشراء أدناه.
**تسلسل الحالة (`status`):** `pending` (أُنشئ التحويل) ← `in_transit` (خرجت البضاعة فعلياً من الفرع المصدر، يجب خصمها من `stock_levels` عند هذه الخطوة) ← `received` (استُلمت في الفرع الهدف، تُضاف إلى `stock_levels` الخاصة به) — هذا يمنع ازدواج الكمية أو فقدانها أثناء النقل.

### 5.6 جداول `purchase_orders` و `purchase_order_items`
نفس نمط "رأس + تفاصيل": أمر شراء واحد من مورّد معيّن، يحتوي عدة أصناف بكمياتها وتكلفتها. عند تغيير `status` إلى `received`، منطق الباك إند (يُبنى لاحقاً بنفس نمط `InvoicesController`) يزيد `stock_levels` تلقائياً لكل صنف في `purchase_order_items`.

### 5.7 جداول `stock_counts` و `stock_count_items`
**الغرض:** الجرد الدوري — مقارنة الكمية النظامية (`system_quantity`) بالكمية الفعلية المعدودة يدوياً (`counted_quantity`).
**عمود محسوب (`Computed Column`):** `variance AS (counted_quantity - system_quantity) PERSISTED` — يُحسَب تلقائياً من قِبل SQL Server نفسه (وليس الباك إند)، فلا يمكن لأي خطأ برمجي أن يُدخل قيمة فرق خاطئة؛ `PERSISTED` تعني القيمة تُخزَّن فعلياً على القرص (لا تُعاد حسابها في كل قراءة)، مما يسرّع تقارير الفروقات الكبيرة.

## 10. استراتيجية الفهرسة (Indexes) الموصى بها

المفاتيح الأساسية (`PRIMARY KEY`) وقيود `UNIQUE` مفهرَسة تلقائياً من SQL Server. بالإضافة لذلك، يُنصَح بإضافة الفهارس التالية عند بدء استخدام حقيقي بحجم بيانات (لا حاجة لها من اليوم الأول بحجم بيانات صغير، لكن تسجيلها هنا يمنع نسيانها):

```sql
-- تسريع شاشة POS عند البحث بالباركود (استعلام متكرر آلاف المرات يومياً)
CREATE INDEX IX_products_org_barcode ON products(organization_id, barcode) WHERE is_deleted = 0;

-- تسريع تقارير المبيعات حسب التاريخ لكل فرع
CREATE INDEX IX_invoices_branch_date ON invoices(branch_id, created_at DESC);

-- تسريع فحص نقص المخزون (يُنفَّذ عند كل عملية بيع)
CREATE INDEX IX_stock_levels_branch_product ON stock_levels(branch_id, product_id);

-- تسريع البحث عن بطاقة عميل عند المسح في POS
CREATE INDEX IX_customers_card_barcode ON customers(card_barcode) WHERE is_deleted = 0;

-- تسريع سجل التدقيق عند البحث حسب المستخدم أو الجدول
CREATE INDEX IX_audit_logs_org_date ON audit_logs(organization_id, created_at DESC);
```

**قاعدة عامة للتوسّع:** أي عمود يظهر بكثرة في جملة `WHERE` أو `ORDER BY` في استعلام يُنفَّذ عشرات/مئات المرات يومياً (وليس تقريراً نادر التنفيذ) يستحق فهرساً. لا تُفهرِس كل عمود احتياطاً — كل فهرس إضافي يُبطئ عمليات `INSERT`/`UPDATE` قليلاً.

## 12. قائمة تحقق (Checklist) لأي جدول جديد تضيفه مستقبلاً

قبل كتابة `CREATE TABLE` لأي جدول جديد غير موجود أصلاً في المخطط، تأكد من:

- [ ] المفتاح الأساسي `UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID()`
- [ ] عمود `organization_id UNIQUEIDENTIFIER NOT NULL REFERENCES organizations(id)` (باستثناء جداول تعريفية عامة جداً نادرة جداً مثل `permissions`)
- [ ] هل هذا الجدول "تشغيل يومي داخل فرع"؟ إن كانت الإجابة نعم → أضف `branch_id`
- [ ] هل يحتوي بيانات مالية أو مخزونية يجب حفظ تاريخها؟ إن كانت الإجابة نعم → `is_deleted BIT DEFAULT 0` بدل حذف فعلي، وامتنع عن استخدام `ON DELETE CASCADE` على أي علاقة تشير لبيانات تاريخية
- [ ] `created_at DATETIME2 DEFAULT SYSUTCDATETIME()`
- [ ] المبالغ المالية: `DECIMAL(14,2)` — أبداً `FLOAT` أو `MONEY`
- [ ] الكميات: `DECIMAL(14,3)`
- [ ] أضف Security Policy مطابقة (`fn_TenantPredicate` إن كان يحمل `branch_id`، أو `fn_OrgOnlyPredicate` إن لم يحمله) — راجع نهاية `DATABASE_SCHEMA_SQLSERVER.sql`
- [ ] سجّل الجدول في `ARCHITECTURE.md` تحت الموديول المناسب قبل البدء بالتنفيذ الفعلي، حتى تبقى الوثيقة مصدر الحقيقة الوحيد كما هو متفق عليه من بداية المشروع
